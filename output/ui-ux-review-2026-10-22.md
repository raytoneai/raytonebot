# RaytoneBot UI/UX 评估 · 2026-10-22

结论：有明确优化空间，优先修正操作语义与产物阅读空间。现有基础库足够，不建议为匹配帖子而整体迁移 shadcn Nova，或引入 dnd-kit / Zustand。

本次仅评估，没有修改产品代码、设置或调用模型。依据：当前源码、`.impeccable.md` 和产品进度，以及本机 1280×720 浏览器中的现有对话、HTML 产物、设置页和 Tool approval 演示。未验证手机、暗色主题、真实运行中的排队操作，也没有进行用户测试。

Nova 在官方说明里主要是缩减 padding/margin 的紧凑风格，不会自动解决操作含义、审批和结果发现问题：[shadcn create 官方说明](https://ui.shadcn.com/docs/changelog/2025-12-shadcn-create)。shadcn Resizable 同样基于我们已用的库：[官方 Resizable 文档](https://ui.shadcn.com/docs/components/base/resizable)。

GSAP 用于 HTML 产物沙箱，主 UI 未直接使用；因此它和主界面的 Motion 有不同职责，不应仅凭依赖列表判断重复。

## 优先改进

### P1 · 审批的“选中”与“立即提交”混在一起

浏览器实见：三个编号选项“允许 / 始终允许 / 拒绝”，底部再次出现“拒绝 / 允许”，提示为“使用 Tab / 上下键选择，回车确认”。源码中，上方选项点击会直接调用 confirm，并非先选后统一确认。尤其“始终允许”容易被误解为尚未提交的选择。

建议：沿用现有 approval owner，统一为“选中后确认”；明确当前选择及授权范围，取消底部重复的第二套决策。也可采用直接动作式设计，但按钮、提示语必须一致，不混用两种模式。保留当前权限边界。

证据：`src/components/agent-preview/chatframe/approval.tsx:177`；真实默认 inline 路径 `src/agent-shell.tsx:433`。适合 `/clarify`、`/distill`。

### P1 · 排队发送被主题画成普通发送箭头

源码发现：“加入队列”使用 `.send-button`，native 主题将该类的文字设为透明、原 SVG 隐藏，再用伪元素绘制发送箭头；停止按钮有独立处理，队列没有。用户难以从图形判断补充内容会排队还是立即生效。

建议：为队列保留“排队发送”文字或独立队列图标；“插话”补充短说明“下次模型调用前生效”，停止保持独立。避免三个动作同等突出。本项需在真实运行且有草稿时补视觉复现；本次没有发起模型任务。

证据：`src/components/agent-preview/ComposerFrame.tsx:810`、`:813`；`src/styles/app.css:10184`、`:10217`、`:10221`、`:10491`。适合 `/clarify`、`/polish`。

### P2 · 产物预览的默认宽度不足

1280px 窗口实见：侧栏展开时，右侧输出约 316px，文件详情行中的文件名和路径同时省略；HTML 标题折成三行，正文预览狭窄。当前提供拖动和展开按钮，但初次打开仍需手动调整。分栏组件没有保存用户调整后的比例。

建议：打开 HTML/PDF 等阅读型产物时，在空间允许下给输出约 40–45% 作为待验证起点；保留手动调整并记住比例。根据可用宽度验证聊天最小宽度，不能直接将这个比例套到手机。保持现有四个输出页签。

证据：`src/components/shell/RightPanelLayout.tsx:18`；`src/exported-project.ts:220`。适合 `/layout`、`/adapt`。

### P2 · 搜索无结果被描述为目录为空

源码中，工作区文件列表无论是否正在搜索，零结果都使用“此目录为空”。搜索不存在的关键词时，这会让用户误判文件丢失或工作区不对。

建议：区分“此目录为空”和“没有匹配的文件”；后者显示当前查询并提供清除搜索。继续由 OutputFrame 持有，不新增面板。

证据：`src/components/agent-preview/OutputFrame.tsx:197`、`:207`；`src/i18n/copy/workspace.ts:218`。适合 `/clarify`。

## 保留与次优先项

当前视觉克制，有自己的 Bot 身份；没有营销大字报、重复卡片网格等模板感。聊天行宽和留白已有控制；输出四个来源并列明确；设置页按功能导航、页内折叠，结构清楚。无需因设置项超过四个就判定认知负荷过高。

保留已由用户确定的 Logo 创建 Bot、右键编辑、居中标题、消息左右区分、历史按 Bot 分组及首页隐藏工作区。若优化入口，只补不打扰的提示，不反向改回旧结构。

次优先：Bot 编辑页将外观设为可展开区域，减少只改名字时的干扰；普通截断历史标题补完整提示；ReasoningBlock 和 ToolCallCard 的 Motion 折叠动画补齐减少动态效果偏好。无需新增动效库。

## 启发式评估

以下为有限范围的设计判断，0–4 分，不是可用性测试结果；未逐条实测所有流程。总分仅用于定位薄弱项，不作为全产品验收。

| 原则 | 分数 | 依据 |
| --- | ---: | --- |
| 状态可见 | 3 | 已有运行、工具和队列状态 |
| 符合用户语言 | 3 | 主要动作有中文；部分行为含义不明确 |
| 控制与退出 | 3 | 有停止、取消、草稿、队列控制 |
| 一致性 | 2 | 队列视觉与实际行为不一致；审批混用两种模式 |
| 防错 | 3 | 已有审批和删除确认，授权交互仍可改进 |
| 识别而非记忆 | 2 | 部分入口和截断标题仍依赖发现或记忆 |
| 效率 | 3 | 键盘和历史能力已有，产物需手动调宽 |
| 简洁 | 3 | 主聊天清晰，审批重复；编辑外观可渐进展开 |
| 错误恢复 | 2 | 搜索空态不准确；尚未完整实测异常路径 |
| 上下文帮助 | 2 | 已有提示，但审批提示与点击行为不一致 |
| 合计 | 26/40 | 有可用基础，交互语义值得优先改进 |

认知负荷初评：8 项中约 3 项存在局部问题——运行中动作的区分、审批重复决策、编辑页缺少渐进展开。主聊天并未表现出全局过载。

从不同使用方式看：首次使用者可能把审批选项当作待确认选择；高频使用者更受产物窄屏、长标题截断和搜索空态影响；单用户工作助手最需要减少的困惑是“接下来会执行什么、是否已经授权、结果在哪里”。

## 检查边界与建议顺序

独立源码评审与浏览器观察支持上述结论。限定五个核心组件执行 `npx --yes impeccable --json`，约 90 秒无输出后终止；没有检测 JSON，自动检测问题数与误报数均未知，不能写作零。浏览器未注入检测覆盖层。

建议第一轮：`/clarify` 修审批和排队动作 → `/layout` 调产物阅读空间 → `/clarify` 修搜索空态 → `/polish` 收尾。实施时沿用现有 owner，按需新增状态区分；分别验证审批提交次数与授权范围、真实运行中三种补充动作、桌面/窄屏分栏，以及空目录与无匹配搜索。当前仅完成评估。
