# 审批失败原因修复 · 2026-10-30

> 历史初稿：用户随后否定这套错误/重试展示，现已由[审批等待与决定确认](../approval-flow-2026-10-30/README.md)取代。下文只记录当时的实现和验收。

审批提交不再丢弃状态与原因。沿用 `approvalSubmission` 和两种既有审批表面，显示中英日的原因及下一步；原始错误在“查看错误详情”中按纯文本展开，限长并换行。没有增加审批组件、接口或自动重发。

- 连接或超时：说明送达尚未确认，核对状态后才手动重试。
- 登录、来源限制或无法识别的请求：说明重新进入/刷新方法，按钮刷新页面，不继续发送无效决定。
- 限流或服务不可用：稍后核对状态再重试；保留原选择与原会话/轮次/工具身份。
- 409 已结束/已回答：沿用正常收起行为，不制造失败提示。

## 验证

- 初始 API 用例先复现状态丢失；真实 Chromium 中两种审批表面先复现只能显示通用失败提示。修复后定向 19 项通过（`targeted-tests.log`）。最后收紧网络错误分类后，完整测试再次通过 635/635，无跳过（`tests.log`）。
- 浏览器回归使用生产组件、React 和 piClient，在 HTTP 边界控制响应；覆盖 503 详情、拒绝选择保留、重试同一身份、409 收起、中英日的 401/403/400 恢复、刷新不重发、双击单提交、连接丢失和超时。超时浏览器用例缩短等待时间，API 用例另核对实际 15 秒预算。
- `npm run build` 通过（`build.log`），仅原有大 chunk 提示。
- 一次与构建同时运行的全量复验中，既有 popup 下载测试报 `popup click stalled`（`tests-concurrent-build.log`，634/635）；未修改该测试或浏览器实现，单独复跑通过（`download-recheck.log`），随后完整测试复跑通过（`tests.log`）。并发负载是可能原因，未断言已证明根因。

- `node scripts/cloud-preview.mjs --check` 通过（`cloud-check.log`）。
