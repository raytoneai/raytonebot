# RaytoneBot：面向 Sandbox 的优化评估

日期：2026-10-03。状态：建议，未改变已采纳的 ADR、产品路线或运行代码。

依据：四份现有调研/部署报告、`docs/product/`、`issue.md` 与当前实现。平台的 50 小时窗口、约 1.2 秒唤醒、访问不自动唤醒来自仓库内既有实测记录，本次未重新操作云实例。外部文档仅用于校验底层机制，不把官方 E2B 新版本能力等同于 AgentSphere fork。

## 判断

继续保留 React/AgentUX UI、Pi 与现有 CLI 接入。最有价值的投入是让任务、数据和权限适应沙箱生命周期：浏览器可断线，应用可重启，实例可替换，而任务结果和重要产物有明确归属。

AgentSphere 底层本身使用 Firecracker microVM。这里“Sandbox 与 VM 的区别”主要是服务契约：实例由平台管理、有运行期限、可暂停/恢复、可按需重建，不能依赖它永久在线或本地磁盘永久存在。不要将这些限制推广为所有 sandbox 平台的固有属性。

现有基础已有相当部分完成：Pi 文件会话、产品对话记录、CLI session id、角色目录、共享目录、部署脚本、暂停/恢复及本机备份。当前重点是补足这些机制的闭环。

## 优先处理的实际缺口

### P0：任务执行独立于浏览器连接

`src/pi/piHost.ts:581` 在响应连接关闭时调用 `controller.abort()`。因此当前即使沙箱仍在运行，关闭页面或网络中断也会取消任务，与“电脑关机后继续工作”的产品目标存在直接差距。已有 5 秒心跳只能减少空闲代理断流。

最小方案仍在现有 Node 服务内：

1. 提交先生成并持久保存稳定的任务 ID、请求 ID、参数摘要和状态，再确认接纳；重复同一请求返回同一任务，内容冲突则拒绝。
2. 运行由服务持有，事件流只是订阅者。浏览器断开只取消订阅，用户明确点击停止才取消对应任务。
3. 复用现有 AgentUX 事件，历史与实时流使用一致、单调的序号；按游标补读，并处理订阅与读取历史之间的竞争，防止漏事件或重复文本。
4. 单用户阶段保留一次一个任务；运行名额在第一次异步等待前获取，忙时明确拒绝。无需先引入队列服务或多 Agent 并发。
5. 后台运行有时长、输出量和模型消耗上限，断开页面不等于允许无限运行。

需要一起补任务状态：`queued/running/awaiting_approval/completed/failed/cancelled/interrupted`。`running` 当前只是内存布尔值，审批等待也是内存 Promise（`approvalGate.ts:72`）。进程重启后不能仅凭历史审批卡片认定原工具仍能批准执行；不能恢复执行句柄的轮次明确标记中断，不自动重发。

`piHost.ts:418` 当前每 40 个事件或遇到审批才落盘，结束时再 flush。应对任务接纳、工具开始/结果、审批决定、终态这些关键事实及时落盘，文本增量可按时间/大小批量写。提交幂等与事件日志都不能保证外部副作用“恰好一次”；结果未知时保持未知/中断，核实后再由用户决定下一步。

验收：无模型假执行器覆盖关页后继续、重连补流不重复、重复提交只执行一次、明确停止、进程重启后中断且不重放。再补真实模型长任务验收。

### P0：将“有备份命令”提升为“新实例可恢复”

`scripts/agentsphere/sandbox.py:33` 仅备份 `~/.raytonebot/data` 与 `/home/user/workspace`。产品记录保存了 Claude/Codex session id，但 `cliHarness.ts:344`、`:428` 未显式把两者原生会话文件归入这一备份范围。保存 ID 不能替代原生上下文文件；原生 session 丢失时，现有实现还可能退回新会话。

目前应把“三引擎在全新沙箱上能继续原会话”记为待验收，不能从原实例重启、暂停/恢复的成功推出这一结论。

建议：

- 明确数据清单：产品记录、Pi 上下文、Claude/Codex 必要原生会话文件、工作成果、非敏感恢复配置；记录引擎版本与工作目录映射。显式配置应用管理的 CLI 状态目录，并验证对应版本的路径行为。
- 原生状态只备份允许的文件，不整包复制个人配置、认证文件或整个 HOME。工作区本身也可能包含敏感文件，备份不能仅因排除了 env 就宣称完全不含秘密。
- 备份前停止接纳新任务，在一致性边界 flush；不要边写文件边假设 tar 是一致快照。
- `sandbox.py:161` 会忽略读取失败，且归档非空就可能被视为成功。改为报告缺失文件/打包错误，保存清单、版本、大小与校验值，并验证归档可读取。
- `sandbox.py:178` 先解包后停服务，恢复时存在旧进程继续写入、覆盖新数据的风险。应先停写/停服务，验证归档路径与内容，再恢复和启动。
- 可重建依赖、缓存不纳入默认备份，避免 workspace 中的 `node_modules` 等不断放大包体；必要的离线依赖另列清单。
- 做新沙箱恢复演练：列表和产物存在、三引擎记得原上下文、权限仍有效。此前不要销毁旧实例。

近期继续使用本机作为实例外备份位置。若要求电脑关机期间也有备份，再选择用户认可的远端存储与受限上传身份。设定明确恢复目标，例如每日一次备份意味着最坏可能损失约一天数据；“15 分钟重建”须实测。

### P0：补齐沙箱内部的权限边界

沙箱外层隔离保护宿主与其他实例，不能隔离同一沙箱、同一系统用户下的 bot 和 Agent。`permissionPolicy.ts:85` 主要通过命令文本匹配识别受保护操作；路径别名、符号链接或程序间接访问不能靠继续加正则变成可靠隔离。

`cliHarness.ts:226` 的子进程没有切换 UID/GID；模型服务模式下 Claude 需要的 token 被放回环境。Codex exec 又不经过逐工具审批。上述问题在现有文档也已承认，应将 S1 从远期加固前移。

最小可行实施方向：

- bot 与执行工具使用不同非特权系统用户；应用目录与凭据由执行用户无权修改/读取的账户持有，工作区单独授权。
- Pi 的 read/write 等工具目前直接在 bot 进程执行（`piHost.ts:644`）；只给 CLI 加 UID 不够。Pi 工具执行也要进入受限 worker，或增加可证明的文件/进程隔离边界。这可以是本地子进程，不需要新增网络服务。
- 模型请求需要进一步隔离时，在现有 bot 服务内增加仅面向固定上游的模型代理，给 Agent 短期、限定模型与额度的 token；它降低长期 key 暴露，不能阻止授权额度内的滥用。代理路由不能变成任意 URL 转发器。
- 调查实例内提权能力、sudo、挂载及 `/proc` 可见性；独立账户只有在执行用户无法恢复高权限时才构成边界。
- 保留工作区内可逆操作自动执行；发布、上传、跨主机访问与凭据访问单独授权。未补全 Codex 协议前，明确其仅为整轮授权，不能宣称所有引擎都有同等逐步审批。评估 `app-server` 时单独做执行前阻断验收。

验收覆盖三种引擎：允许访问工作区，无法读取 bot env、改应用或经符号链接越界；审批拒绝时真实副作用未发生。用无价值测试凭据验证，避免把真实 key 放入测试输出。

## 如何发挥 Sandbox 优势

| 能力/约束 | 利用方式 | 边界 |
| --- | --- | --- |
| 快速恢复，仓库记录约 1.2 秒 | 日常回到原工作区优先 wake，避免每次重装依赖 | 这是既有单次实测，不是启动时延 SLA；恢复后还需应用 health |
| 可暂停 | 任务结束、状态写稳并完成备份后，闲置再暂停 | 当前默认 50 小时是运行窗口上限，不是闲置检测；暂停期间定时器和任务均不执行 |
| 可重建 | 固定运行环境、锁文件与部署流程；污染/故障后可替换实例 | 自定义模板、快照克隆等能力要先核对 AgentSphere，不直接照搬新版 E2B API |
| 执行环境与个人电脑分离 | 在受限工作区内让 Agent 安装依赖、测试和生成临时产物 | API 调用、发布与上传的外部副作用不会因丢弃沙箱而撤销 |
| 可创建多个环境 | 有独立高风险任务时，后续用专用短期沙箱，验收产物后再交接 | 现在 2C/4G 单实例先保持串行；无需先做多实例调度平台 |
| 算力与状态可分离 | 把成果文件、任务记录、必要上下文放入明确备份范围；其余可重建 | 暂停快照只是恢复手段，不能替代实例外备份 |

产品上最适合优先做好“执行一个有边界的任务，保存结果，用时回来继续”：代码修改、批量文件处理、报告生成、测试与预览。7×24 小时监听、严格定时触发、持续外部连接只有在明确需要且具备实例外唤醒能力时才承诺。

## 唤醒与恢复应分层设计

实例和 UI 都暂停后，实例内代码无法接到请求并唤醒自己。当前平台 HTTP 访问不唤醒，必须明确选择：

| 使用要求 | 最小方案 |
| --- | --- |
| 接受用电脑手动启动 | 沿用本机 `sandbox.py wake`，补应用 health 和故障分类，不增加服务 |
| 手机打开就能用、电脑关机仍能定时启动 | 需要实例外的极小入口/调度器：认证用户、绑定固定实例、resume、health、转发或返回已就绪地址 |
| 更简单的长期方案 | 向平台确认代理自动唤醒、暂停保留期限、可靠持久化与故障恢复能力 |

如新增实例外入口，团队 key 仍不能进浏览器或 Agent 沙箱；优先使用平台提供的受限权限。暂时只有团队 key 时要明确管理边界，不向用户暴露任意实例管理接口。此部署位置涉及 ADR-006，应在实际实施前单独确定；本评估没有部署外部服务。

建议恢复顺序：确认实例状态 → wake → 检查进程/HTTP health → 必要时启动已有服务 → 核对任务状态 → 重连事件流。实例真的不存在才进入“新建 + 恢复备份”；未知错误或短暂 502 不能触发自动创建新实例。

还要区分四种故障：

| 故障 | 应有行为 |
| --- | --- |
| 浏览器断线，执行端仍正常 | 任务继续，回来补读；不重发 prompt |
| 沙箱暂停 | 保留现场，外部唤醒；恢复后检查网络与任务是否仍有效 |
| bot/CLI 进程崩溃 | 已完成记录可读；无法续接的运行标记中断，不自动重放 |
| 整个实例丢失 | 从外部备份重建；告知备份时间与数据缺口 |

Firecracker 官方明确说明快照恢复不保证网络连接状态保留。因此“相同 PID/文件恢复成功”不等于“运行中的模型请求无损续跑”，更不能据此自动重试可能已产生副作用的工具。[Firecracker snapshot 文档](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)

官方 E2B 文档目前描述了 connect 自动恢复等行为；AgentSphere 的仓库实测与之不同，应继续使用 fork 已验证的接口，保持兼容范围。[E2B persistence 文档](https://docs.e2b.dev/sandbox/persistence)

## P1：成果交付、资源与启动成本

1. **前移文件上传/下载。** 复用 composer 附件入口与 Output 面板，实现“输入文件 → 执行 → 下载成果”；可丢弃环境的产物必须容易取回。下载使用受控路径/产物 ID，防止路径穿越和符号链接越界；用户生成的 HTML 预览应隔离来源，避免与 bot 的认证页面共享权限。
2. **修正历史保留策略。** `conversationStore.ts:84` 超过 200 条时直接删除旧记录，且未同步清理 Pi 原生会话。将其改成明确的保留/归档策略；不要因性能上限静默删用户历史。
3. **按证据优化事件存储。** 当前全量 JSON 同步重写（`conversationStore.ts:65`），列表读取还会缓存所有会话事件。长会话可评估追加 JSONL + 小型元数据索引与按需加载；若真正需要事务队列/跨会话查询，再评估 SQLite。先做规模测量，不把引入数据库当作当前前置条件。
4. **缩小部署扰动。** 已有 lock hash 跳过重复 `npm ci`，应保留。当前部署在旧服务仍运行时覆盖应用目录（`deploy.py:123`，停服务在 `:160`）；改为阻止新任务、等待/明确中断活动任务、准备新版本后切换，health 失败可回滚应用文件。回滚应用不代表回滚用户数据。
5. **补应用 health 与有限重启。** 现在 `status` 只查平台状态（`sandbox.py:120`），进程由 nohup 启动。复用模板现有的进程监督能力（如有），区分“实例运行”“HTTP 存活”“运行时可接任务”；health 不必每次调用模型。
6. **最后处理前端与生产依赖。** 本次入口 JS 约 1,274.54 kB，gzip 401.01 kB，存在 chunk 告警。Mermaid 与演示事件已经动态加载，不能把所有构建产物当成首屏请求。先测首屏网络/解析与内存，再考虑设置页、重型预览的按需加载；保持组件与视觉契约。`vite preview` 的生产运行边界可随后收敛为复用现有 `piHost.handle` 的轻量入口，无需新框架。

## 建议实施顺序与验收

| 顺序 | 交付 | 通过标准 |
| --- | --- | --- |
| 0 | 校正现状文档 | 架构、路线图与已实现的持久化、模型来源、脚本一致；不覆盖旧报告的历史事实 |
| 1 | 任务状态 + 浏览器断线恢复 | 关闭页面仍执行；重连无重跑；停止有效；崩溃记录中断 |
| 2 | 完整备份/新实例恢复 | 三引擎上下文与成果恢复；备份缺项会失败；恢复不与旧进程并写 |
| 3 | 内部权限隔离 | 三引擎实际执行均无法读取应用凭据、改应用或越界；保持必要审批 |
| 4 | 上传/下载 + 生命周期 health | 输入/产物闭环；暂停、服务退出、实例丢失可区分 |
| 5 | 按需唤醒/闲置暂停 | 按使用要求选择本机手动或实例外入口；忙碌时不主动暂停；不确定任务不重放 |
| 6 | 资源与包体优化 | 依据量测降低峰值内存、首屏负担和恢复时间 |

步骤 1–3 是同一批最高优先级工作，完成前不应扩大无人值守权限或承诺全天候可靠执行。暂不增加 OpenAgentCore、PostgreSQL、Redis、多实例调度或完整账号平台。
