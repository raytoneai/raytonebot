# 现有 Routines：缺口与最小优化

日期：2026-11-01。基线为首批独立分支 `9a151f1`。用户明确要求优化 RaytoneBot 的 routine 机制；OpenDuet/OpenMausBot 是借鉴来源，不是运行任务的固定输入。此前 README 专用实验已撤出当前改动，本地 stash `f591006` 保留，不进入本批实现。

## 已有能力

`routines.ts` 已提供每 30 秒检查、任务时区与五段 cron、最多 3 分钟的运行时延迟回看、UTC occurrence 去重、忙碌跳过、持久化漏跑说明、最近 20 次记录、等待用户、两次失败停用、定义 revision、重启中断标记。原 Settings Routines 已有编辑、开关、立即运行与结果入口。这些能力保留，不重建调度器、队列或任务看板。

## 按优先级处理的实际缺口

| 优先级 | 复现与影响 | 最小改造 |
| --- | --- | --- |
| P1 | `configure` 尚未结束时停用/删除，随后仍启动；关闭再开启也可能让旧启动复活 | 为未接受启动保留可撤销身份，配置结束后重检；操作成功保存后撤销，晚到失败不计任务失败。已接受运行保留原停止语义 |
| P1 | 会话已保存 success/error/cancelled，但 `routines.json` 终态保存失败；界面卡 running，重启变 interrupted | 按准确 runId 读取已有会话真实终态，保存修正后再展示；恢复时间沿用终态时间，失败计数只算一次；读取失败、活跃运行和合成中断不猜测 |
| P2 | 启用/改排程可能把已过去的分钟记成 offline；重开回补停用期间分钟；墙钟回拨使新任务迟迟不触发；旧记录没有调度基线时推测启动前场次 | 启用/改排程从当前时间之后生效；用原 `nextScheduledAt` 限定本次候选；旧记录先建基线；回拨重置内存检查边界，已接受 occurrence 继续去重 |
| P2 | 首次配置失败没有会话，界面仍提供“打开对话” | 只有当前/保留历史中存在真实 run/message 锚点才启用；以前有结果的任务仍能打开原对话 |

这些问题分别由可控准备屏障、实际 `.tmp` 写盘失败、真实 host/HTTP 重启、可控墙钟和原 owner 浏览器测试复现。验收和限制集中在[本批记录](../output/routine-reliability-2026-11-01/README.md)。

## 保持的边界

- 停用不是停止已接受运行；用户仍在原对话停止。模型准备中撤销的运行不算失败、不伪造交付；重新开启也不恢复已撤销请求。
- 不自动重放中断或失败的工作。恢复只修复已有证据的记录，不重新调用模型或工具。没有原会话证据时保守保留中断，不把“执行结束”视为业务内容完成。
- 沿原文件原子保存和 API，无新字段要求、数据库、通知系统、业务来源限制或外部唤醒服务。普通任务模型、权限和审批不变；`control/`、`console/` 及云平台唤醒继续遵循原分工。
- 保持现有 Vixie cron 兼容语义；`*/n` 日字段并不因为看起来受限就改成另一种日/星期取或规则。审计中的该建议未采纳，核对了 Cronie 的 [entry.c](https://github.com/cronie-crond/cronie/blob/master/src/entry.c) 和 [cron.c](https://github.com/cronie-crond/cronie/blob/master/src/cron.c)。

## 后排事项

通用的“业务检查完整/部分/无变化”和内容去重仍是后续候选：必须先有各任务可核验的证据，不能解析模型一句“没有变化”决定成功或静默。当前先保证任务是否启动、何时生效、是否真正结束这些基础事实可信。更多通知、自动重试/补跑、外部常驻和调度服务均未纳入本批。
