# RaytoneBot 竞品复评：功能与 UI/UX

初稿：2026-10-29；更新：2026-11-01。初稿 RaytoneBot 基线：`7c85bfa25b8c926ef2dedc51c787fec32148df4c`；OpenDuet 对照基线：`688bcaa6892136f5fcc2f11953e8e47bca38b355`；同日追加 OpenMausBot 时，本地核对以 `08b50093e350973f9194ae9aa54c03d785757543` 工作树为基础。本轮新增两份源码研究，并修正配置续接与交付标签的当前状态；其他竞品沿用下表的固定快照，没有全部重新调研。

## 结论

上轮之后，RaytoneBot 已补齐独立 Bot 配置与上下文、职责起点、Bot 内管理入口、例行任务编辑与运行记录、跨对话产物查找，以及触屏和弹层交互。继续把这些列为“缺失功能”会低估当前版本。

配置续接也已由 T6.8 实现：从失败任务进入模型服务/MCP/Vault/浏览器，保留原请求和附件，由用户显式继续。相反，T6.8 的侧栏交付标签、Bot 汇总和已读追踪已于 10 月 30 日按用户要求整体撤回，不能继续写成已保留的能力或优先补回的缺口。既有运行/审批状态及例行任务运行记录仍保留。[当前续接](../src/runtime/useTaskRecovery.ts)、[撤回记录](../output/remove-result-labels-2026-10-30/README.md)

当前定位可以概括为：**面向单用户、可控且依赖较少的多引擎工作台**。主要长处是现有引擎、审批、浏览器、文件和聊天在同一工作流内；主要差距是首次使用引导、应用连接、后台结果交付、持久成果组织和客户端分发。竞品已经把更多能力串成“提出需求后一路完成”的使用路径，我们仍有较多能力需要用户自己发现、配置和组合。

这是功能和交互结构判断。没有同模型、同任务的对测，不能据此声称我们更聪明、更稳定、更快，或已经达到某个对齐百分比。

## 逐个比较我们的优缺点

| 竞品 | 我们的相对长处 | 我们的差距与实际影响 |

| **OpenMuse** | 我们的独立 Bot 与多引擎适合通用工作；主机结构更轻，不要求 CopilotKit Intelligence 会话服务。 | OpenMuse 明确围绕 Activity、Goals、Ideas 和任务收据组织工作，有邮箱→PDF→填写→审核回复等具体流程、Gmail/Calendar 适配和网页跟踪。我们有工具和例行任务，但用户较难一眼看到“什么完成了、什么等我、下一步是什么”。它的设备推送、语音与完整图形桌面仍在路线图，不能算其现成功能。 |

| **CopilotKit OpenBot** | 对单用户来说，我们的主机、存储与已有引擎集成需要维护的服务更少；现有工作无需引入通用企业 Agent 平台。 | 对方以 AG-UI 接入不同 Agent，提供每 Bot 的电脑、工具策略网关与审计。我们同引擎 Bot 没有独立文件/进程/浏览器隔离，也不是任意 AG-UI Agent 的通用宿主。企业治理与多租户不是当前必追指标。 |
| **OpenDuet** | 我们已有多引擎、定时执行去重、显式配置续接、审批、Vault 与产物查询，且不需要其 Postgres、Intelligence 和每 Bot 电脑的完整部署组合。 | 对方把邮件/日历分流、晨报、任务与可编辑页面组织成具体日常流程，并明确显示检查范围和失败。我们通用能力较全，但缺少现成业务流程。其晨报自动入口由打开 Chat 触发，不是默认的定时推送；Make 保存也不是不可变历史版本。 |

## OpenDuet：值得学什么，怎样落到现有产品

OpenDuet 是建立在 CopilotKit OpenBot 上的主动助手模板，增加晨报、Tasks、Make 和场景 Skills。品牌/Bot/Skill 配置集中在 tenant package，但完整能力还涉及服务端、前端和数据库迁移，不能只复制几份 YAML 就移植。它的价值主要在业务闭环与状态表达；没有证据支持为此替换 RaytoneBot 的运行时、事件协议或存储。[固定 README](https://github.com/CopilotKit/OpenDuet/blob/677e0fcd148d80b99dd788c6d6f9c1c9f40a72db/README.md)、[实现范围](openduet-source-research-2026-11-01.md)

### 1. 先做可重复完成的任务，再扩功能清单

把“有搜索、浏览器和文件工具”变成“带来源的比较报告”“检查变化后更新文档”等具体流程，每个流程写明输入、能力要求、交付物及失败条件。OpenDuet 的场景 Skills 和 Google 工作流是参考；RaytoneBot 已有文本 Skills、按 Bot 分配与按需读取，可以先写两三个任务配方验证效果，不需要新插件框架。其后才考虑在现有欢迎区/Composer 暴露更便捷入口。[OpenDuet 研究](openduet-source-research-2026-11-01.md)、[本地 Skills](../src/pi/botSkills.ts)

先复用已有联网能力做研究报告最省改动；若邮箱/日历确实成为高频需求，再选一个连接流程。Skill 中写了需要某工具不等于已经授权，当前工具清单、账号状态与主机权限仍须分别检查。

### 2. 让结果说清检查范围和不确定项

OpenDuet 的事项分流先用规则处理明确可等待的项目，其余交模型；保留判断理由与来源。晨报会标记未分拣事项，并列出无法检查的来源、数量上限和截断。模型失败不应被包装成“没有待办”，读取了部分数据也不应说“全部检查完毕”。这些是值得借鉴的结果语义；本轮只核对代码，没有验证分类准确率。[分流与晨报证据](openduet-source-research-2026-11-01.md)

我们产物查询已有 `truncated`/`unreadable` 及相应展示，不能重复当成新缺口；例行任务则主要记录运行是否成功，没有统一表达“完整查过且无变化”和“仅检查部分来源”。可先通过任务 Skill 约定证据、覆盖范围与待核验事项；若后续需要主机据此减少重复报告，再定义可校验的结果字段，不能仅靠解析一段模型文案。[产物查询](../src/pi/artifactCatalog.ts)、[现有展示](../src/components/agent-preview/outputframe/OutputContent.tsx)、[例行任务类型](../src/pi/routineTypes.ts)

### 3. 区分执行去重、内容去重和打扰控制

OpenDuet 的晨报通过服务端按日期认领和同事务入队防止多窗口重复创建；主动任务引擎另外使用增量检查、已打开事项和近期隐藏事项控制重复。标题规范化能挡住同标题重复，语义改写仍有提示词依赖，不能视为完整语义去重。晨报前端还会给正在输入或进行中的工作让路。[去重与触发证据](openduet-source-research-2026-11-01.md)

RaytoneBot 已有 occurrence 身份、持久去重和会话记录兜底，不需要重新造执行调度器。真实增量是同一任务第二天没有新事实时如何减少重复内容、检查失败时如何保留可追溯记录；当前提示词仅要求无事可报时说一句话，仍会产生回复。应先在一条现有例行任务里验证这些区别，保留失败和审批，不恢复侧栏“新结果”标签。[本地调度与提示词](../src/pi/routines.ts)、[用户纠正](product/09-lessons.md)

### 4. 把配置、可连接与任务可执行分开

OpenDuet 的 Setup/Google 流程区分部署启用、OAuth 配置、Bot 工具授权、个人账号连接和实际检查；这比只看 URL 或密钥是否填了更接近用户任务。我们 MCP 已有真实 `tools/list` 测试、错误与检查时间，不必新增重复测试入口；尚可补的是具体 Skill 需要的工具是否齐全，以及实际业务读取是否成功。应复用 SettingsDialog 与现有显式续接，不能关闭设置即自动发送原动作。[OpenDuet 连接证据](openduet-source-research-2026-11-01.md)、[本地 MCP 检查](../src/pi/mcpServers.ts)、[续接行为](../src/runtime/useTaskRecovery.ts)

### 不宜照搬

- **整套基础设施**：Bun/Hono、Postgres/pgvector、Intelligence 与每 Bot computer 面向其平台需求；当前没有理由给单用户主机增加这些服务。AG-UI 与 AgentUX 也不能直接互换。
- **新增 Tasks/Make/晨报面板**：参考其流程，先复用现有聊天、Settings 和 Output。新入口仍须按本项目规范先定 owner 与验收，不能另起平行组件。
- **把原地保存叫版本历史**：Make 有并发冲突检查，仍更新同一页面；checklist revision 也不是历史内容快照。我们“交付文件保留当时版本”的建议仍来自 Rakazo 和本地文件恢复缺口，OpenDuet 没有补证这个能力。
- **整轮失败自动重跑**：其 task engine 最多尝试两次，异常或重启可能再执行一轮。我们对结果不明的动作先核对，不自动重放；不能为了恢复方便而引入重复对外动作的风险。
- **把主动等同于默认打扰**：打开 Chat 才认领的晨报、后台 routine 和消息通知是不同链路；源码存在不代表全天候可靠推送，更不构成重新加入用户已拒绝提示的理由。

外部事实、固定提交链接与未验证边界集中见[OpenDuet 一手研究](openduet-source-research-2026-11-01.md)。以上是候选改进，没有引入依赖、改运行时代码或改变模型。

## OpenMausBot：更接近现有架构，重点看配置复用和外部编排

从部署结构看，OpenMausBot 比 OpenDuet 更接近 RaytoneBot：本地 CLI 执行，主机统一处理命令、事件和状态，前端展示结果；Electron、Boat 电脑和 Composio 连接器补齐桌面与外部应用体验。它的启示是怎样把已有运行能力做成可复用、可被其他工具调用的产品，不是再增加一种引擎或换事件协议。[固定 README](https://github.com/milind-soni/OpenMausBot/blob/8c663d2b7647dcea04a2278dd0f794f591ae95e0/README.md)、[源码研究](openmausbot-source-research-2026-11-01.md)

| 借鉴点 | RaytoneBot 当前状态 | 最小适用方向 |
| --- | --- | --- |
| 可审阅的团队配置包 | 已有 Bot 人设、群成员、文本 Skills 和例行任务；`/bots/import` 只迁移旧浏览器配置，不是团队包。 | 先把高频任务的角色、步骤和产物要求写成可读配方；确需反复建立同一组 Bot 时，再评估白名单配置包、导入预览与新身份映射。不要直接导出整个数据目录。 |
| 有限的外部 MCP/CLI 控制面 | 已有主机 HTTP、产品内工具和 Claude 控制通道 MCP；没有等价的面向外部客户端的产品控制入口。 | 有实际 Codex/脚本协作需求时，复用主机提供发送、查状态、读取结果、停止等有限操作；权限审批继续留在用户既有入口，不暴露密钥或任意管理路由。 |
| 明确协作任务何时真正结束 | 群前台回合可以结束，后台只读委派继续工作；已有持久任务身份、分页结果与 `needs_review`。 | 若提供外部等待接口，应同时检查请求及其委派，区分完成、待审批/提问、超时和结果未知，不能仅看首个回复结束。无需给侧栏增加结果标签。 |

本地依据：[Bot 导入](../src/pi/botConfig.ts)、[内部 MCP](../src/pi/cliHarness.ts)、[委派生命周期](../src/pi/groupDelegation.ts)、[任务记录与恢复](../src/pi/groupTasks.ts)、[现有命令](../package.json)。上表后两项是有使用需求后的接口候选，当前不立项新服务或 CLI。

上游等待语义也有边界：`job` 与 `turn` 是不同范围，汇总只等待需要回报的相关任务链；主任务显示 `completed` 时，仍可能在原因和计数里记录队友失败或取消。应同时保留总状态、子任务结果与待处理原因，不能把“等待结束”当成“所有工作成功”。[实际汇总实现](https://github.com/milind-soni/OpenMausBot/blob/8c663d2b7647dcea04a2278dd0f794f591ae95e0/server/job-view.ts)

**团队导入尤其不能只看 README 的承诺。** 固定版本 README 写“导入后 Ask”，实际普通文件导入没有显式设置审批模式，会继承普通本地默认的 Full access；这是产品审批模式，不等于本次验证了操作系统权限或隔离。`.md` playbook 与包文件最终走同一导入链，不能把差异归因于格式。普通导入会关闭连接器和 Skills、暂停 routines，但组织库导入存在开启 Skills 的例外。[默认值与导入链](openmausbot-source-research-2026-11-01.md)

此外，v2 团队包允许选带 starter notes，不能笼统说“不导出记忆”；排除独立凭据字段与扫描文本中的疑似秘密，也不能保证任意人设/笔记都没有私密内容。若未来借鉴，应采用明确字段白名单和内容预览，默认不含记忆、权限或账号状态；授权仍由导入者重新确认。[包内容边界](openmausbot-source-research-2026-11-01.md)

这轮新增参考不会改变报告的最小优先级：**先把现有 Skills 做成有效任务配方，再决定是否需要团队包和外部编排入口。** 桌面安装、语音、组织治理与云电脑是不同范围，不能因为对方已有入口就一起引入；现有选定模型和群路由也不因它支持 Jev 而改变。

## Rakazo：既有四项建议的现状

### 1. 从“配置一个 Bot”走向“完成第一件事”

Rakazo 首次设置会连接模型并创建或复用 Chief；它的介绍以具体工作职责组织入口。我们现在有研究/规划/实现三个职责起点，但本质上填入人设文本，不会自动完成能力准备，也没有完整的首个任务引导。

对新用户而言，“帮我对比两个产品并输出报告”比“选择引擎、能力与长期要求”更容易开始。建议在现有欢迎区提供少量可编辑任务起点，按当前可用能力说明需要什么，避免再增加一层独立引导面板。依据：[Rakazo Onboarding](https://github.com/elie222/rakazo/blob/45ef441f3ac430f1056b0fe4f49c846291c48d3a/apps/web/src/pages/Onboarding.tsx#L81-L147)、[本项目职责模板](../src/runtime/botRoleTemplates.ts)。

### 2. 配置应出现在任务需要它的时候

Rakazo 的 AppConnectCard 在消息中展示具体应用、授权按钮、等待、连接成功和错误；连接成功后调用携带 Bot/会话上下文的 `appConnected`。这是可以直接核对的交互链路，但本次没有验证 OAuth 后真实任务一定完成。

我们已通过 T6.8 串起“任务遇阻→到对应设置→显式继续”，不再把这条路径列为待开发。当前识别基于错误事件，打开配置页也不等于账号已经可用；下一步应在选定的真实应用流程中核验连接、权限和实际只读请求。已执行轮次使用稳定的新继续请求身份，先核对已有结果，不直接重放原轮。依据：[Rakazo 应用连接卡](https://github.com/elie222/rakazo/blob/45ef441f3ac430f1056b0fe4f49c846291c48d3a/apps/web/src/pages/shell/message-cards.tsx#L145-L239)、[失败识别](../src/runtime/taskRecovery.ts)、[显式续接](../src/runtime/useTaskRecovery.ts)。

### 3. 找回产物之后，还需要看清“哪个版本”

我们已经能跨对话查找产物、定位来源并保留当前预览；这项已不再是空白。Rakazo 则有按产物家族列版本、获取选中版本内容并预览的界面与接口调用。我们历史文件仍指向当前磁盘内容，无法保证重新打开的是当时交付版本。

优先为明确交付的文件考虑不可变快照与版本关联，而不是给所有工作区文件引入版本系统。现有搜索只是元数据查找，扫描有 1000 个会话、20 万事件、2000 个候选产物的上限，不应称为完整全文知识检索。依据：[Rakazo 版本预览](https://github.com/elie222/rakazo/blob/45ef441f3ac430f1056b0fe4f49c846291c48d3a/apps/web/src/pages/Artifacts.tsx#L811-L878)、[本项目查询实现](../src/pi/artifactCatalog.ts)。

Rakazo 本身也有边界：当前关键词/日期仍过滤已载入的页，无匹配时才自动继续翻页；已出现部分匹配不代表搜遍所有页。因此不宜照搬其搜索语义。依据：[当前列表与筛选代码](https://github.com/elie222/rakazo/blob/45ef441f3ac430f1056b0fe4f49c846291c48d3a/apps/web/src/pages/Artifacts.tsx#L112-L180)。

### 4. 自动化需要完整交付，不只是可编辑日程

我们的任务编辑、时区、下次运行、最近运行记录和结果定位已实现。下一步价值是能否可靠获知失败、待处理和新结果。Rakazo 公开提供更多触发方式及移动交互，但它也要求本机保持运行，或部署到常驻服务器，不能理解为设备睡眠后仍自动执行。[Rakazo 运行说明](https://github.com/elie222/rakazo/blob/45ef441f3ac430f1056b0fe4f49c846291c48d3a/README.md)

我们的计时器依赖主机运行，暂停期间错过的较早时刻跳过，不自动补跑；外部运行接口不等于已形成事件连接器生态。例行任务已有成功/失败/等待、错过执行与结果入口；侧栏泛化交付提示已被用户否定。后续优先研究结果内容是否有变化、检查是否完整及如何避免重复报告，沿用任务会话和既有运行记录；新增通知渠道应以明确需求为前提。依据：[任务时钟](../src/pi/routines.ts)、[任务设置](../src/components/settings/RoutinesSection.tsx)、[用户纠正](product/09-lessons.md)。

## UI/UX：现在哪里好，哪里还费力

| 维度 | 当前做得好的地方 | 剩余问题 |
| --- | --- | --- |
| 聊天阅读 | 普通发言标签与用户头像已简化；聊天、产物与输出区职责明确。 | 更多价值应体现在最终成果和下一步，避免结果仍是一大段“做了什么”的文字。 |
| 执行展示 | **保留已有方案：运行中原位显示，整轮结束收为摘要，细节进入右侧控制台。** | 不再把“隐藏执行过程”列为新任务；只在需要用户操作时提供明确入口。 |
| Bot 管理 | 职责起点、顶栏编辑/记忆/任务入口已经补齐，减少全局查找。 | 研究/规划/实现偏通用职责；侧栏仍露出引擎标签，新用户首先看到的未必是用途。可降低技术标签层级，保留详情可查。 |
| 首次使用 | 欢迎区干净、输入突出。 | 空白页主要问“想做什么”，缺少与可用能力对应的首个任务示例。第一次成功仍依赖用户知道产品能做什么。 |
| 例行任务 | 编辑、状态、开关、运行历史和结果入口在同一处，来源可追溯；漏跑/占用有记录。 | 缺少按结果变化抑制重复报告的结构化语义。保持现有紧凑侧栏，不恢复已撤回的“新结果”标签、汇总卡和已读系统。 |
| 手机与键盘 | 已修触屏换行、IME、长草稿、窄屏、焦点返回、快捷搜索和减少动态效果。 | 浏览器模拟不等于真实 iOS/Android 验收；没有自己的原生安装、推送和系统级交互路径。 |

## 建议顺序

2026-11-01 进一步收敛：[优化优先级与最小改造方案](optimization-priorities-2026-11-01.md)对照最新实现，建议首批只做两条任务 Skills 与明确交付文件的版本保留；列明接入位置、兼容行为、验收及其余候选的进入条件。本轮只出方案，未实施。

旧顺序中的“配置与返回路径”已由 T6.8 实现；“侧栏交付提示”曾实现后整体撤回。[T6.8 初次验收](../output/task-flow-2026-10-29/README.md)与[撤回记录](../output/remove-result-labels-2026-10-30/README.md)分别描述当时状态，不能把前者当作当前保留清单。下面按本轮证据重新排序。

按当前“单用户、服务日常工作”的定位排序，优先考虑任务是否能完成、结果是否可靠可找，再考虑首次使用和平台扩张。下表是定性优先级，没有用户频次数据或工期估算；尚未采纳为开发任务。

| 顺序 | 建议 | 用户收益与验收方式 |
| --- | --- | --- |
| **1** | 用现有 Skills 做两三个可验收的真实任务 | 先覆盖带来源报告、已有文档更新；输出可打开的成果、证据和未完成项。复用现有联网/文件能力，不先引入 OAuth 或新服务；同一任务重复执行能判断改善在哪里。 |
| **2** | 为明确交付的文件保留版本 | 同名文件两次交付后能分别打开当时内容，版本与来源对应；先定最小保存范围与保留规则，再由既有 Output 提供选择。OpenDuet 的原地更新不解决此缺口。 |
| **3** | 为例行任务区分无变化、部分检查与失败 | 先用一条任务检验重复结果、来源失败和重启场景；保留运行记录与审批，仅对确认完整且无变化的结果考虑减少重复报告。逻辑归现有 routines，不恢复侧栏标签或新增任务中心。 |
| **4** | 按真实任务补能力预检与应用连接 | 复用 MCP 测试与配置续接，区分已配置、已授权、可读取和所需工具可用；若选邮箱/日历，先做连接→读取→审核写入→回执的一条流程。具体服务仍取决于实际需求。 |
| **5** | 基于实际阻碍优化发现与客户端 | 在现有欢迎区提供可编辑任务示例；真实手机验收先于原生安装、推送、更多委派或独立 Bot 环境。当前紧凑聊天/侧栏和右侧执行详情继续保留。 |

最小下一步是第 1 项：先证明已有工具能稳定完成具体工作，再决定哪些主机字段或入口确有必要。第 2–4 项均为候选，需要独立确定范围，不能把本轮调研当作实现授权。真实任务验收贯穿每项：覆盖长任务、断网重连、进程重启、例行任务跨日及相关手机操作；若发现丢结果、重复执行或权限错误，应优先修复，再推进功能。

OpenMausBot 补充了第 1 项之后的复用方向：同一任务配方确实需要跨 Bot/群或实例重复部署时，再扩成可审阅团队包；需要其他 Agent/脚本调度时，再提供有限控制接口及明确完成条件。这两项没有取代上述交付可靠性优先级。

建议对测使用四个实际任务：带来源且声明覆盖范围的竞品报告；连续两天数据不变、第三天出现变化的例行检查；授权受限的浏览器操作；产物二次修改后找回旧版本。再注入来源读取失败，确认不会误报“无变化”。记录任务成功率、人工介入、重复报告/动作、总耗时、可得成本和结果可追溯性。能用相同模型则对齐；无法对齐时明确引擎、工具与环境差异，避免归因给 UI。

不建议仅为追平清单扩展任意 DAG、多租户、完整桌面控制或大规模连接器市场。当前更值得投入的是让已有能力在真实日常任务中连续完成、容易恢复、容易找到结果。
