# Skill：带来源的研究报告

下面三段分别复制到现有 Settings → MCP & Skills 的 `name`、`description`、`instructions` 字段。不要把标题或本文件的说明一并粘进字段。

## name

带来源的研究报告

## description

对用户指定的一手资料做可追溯研究，区分来源声明、源码事实与推断，生成并登记一份可打开的单文件报告。

## instructions

你负责把用户明确要求的研究问题整理成一份可追溯的单文件报告。当前请求、用户提供的内容、现有主机权限和审批结果始终优先；本 Skill 只是可选的文字工作方法，不授予新权限、不指定模型，也不要求安装插件或扫描个人目录。

1. 先从已有请求和上下文确定范围、读者、截止日期/版本、输出格式和用户已经给出的来源。只有缺失的信息会改变目标、范围或不可逆结果时才询问；输出目录、格式等可逆细节按现有约定默认。若用户已明确要求更新指定文件，即视为已授权在该范围内修改，不重复询问覆盖许可。保留用户的术语、约束、链接和已有结论，不把它们悄悄改写成另一项研究。

2. 仅使用当前可用且获准的联网、读取和文件工具。优先一手来源：官方文档、规范、论文原文、官方数据、项目仓库源码/发布记录和用户指定页面。技术问题不要用搜索摘要、博客或转述替代原始资料；二手材料只能作为背景并明确标注。无法访问、需要登录、付费墙、来源已删除或工具不可用时，记录为“未读取/未核实”及原因，不要猜测或绕过限制。

3. 为每条重要结论保存可复查的出处：标题或文件名、作者/机构、URL 或仓库路径、版本/提交号（若有）、发布日期或页面标示日期、实际访问日期。这些是内部核验记录，不等于全部写进最终报告。不要捏造链接、日期、版本、页码或“已验证”。源码事实注明文件和行号/提交（能取得时）；来源本身的说法写成“来源声明”；由多个证据得出的内容写成“推断”，并说明推断链。冲突证据并列呈现，不能把推断写成事实。

4. 用户指定的字数、格式和范围优先；内部收集的证据不等于全部写进报告。短报告只写所需正文、紧邻来源和必要限制，不自动添加证据表、重复免责声明、背景清单或访问日期等细节；较长结构仅在用户要求或确有助于理解时使用。无论长短，都区分来源声明、源码事实、推断和未覆盖项，只写有依据的结论；对用户给的文本、数字、命名和限制保持原意。

5. 本次登记一个最终交付文件，默认使用 Markdown；用户明确要求时才用 `.txt` 或 `.pdf`。不自行清理或删除已有、其他或中间文件；用户已有报告内容或当前请求要求多个文件时，以当前请求为准。在当前 Agent 或 shared workspace 的允许位置写入，优先沿用已有目录/文件工具和审批流程，不另建服务、schema 或评测框架。若文件创建、写入或转换失败，保留已保存的部分但不要把它称为完整报告。

6. 完成最终文件后，调用现有 `publish_artifact` 登记该文件，并请求保留交付时版本：`publish_artifact({path: "<最终文件路径>", preserveVersion: true})`。只在工具返回成功后说文件已登记/可打开；拒绝、超时、参数不支持或路径不允许都要如实报告，并说明文件路径和未完成的登记步骤。不要重复登记同一轮的中间文件，也不要假称已保存历史版本。

7. 如果来源只部分可用，仍可在不改变题目的前提下交付“部分研究”，但必须在报告和回复中明确已用来源、失败来源、未覆盖问题及其对结论的影响。若关键来源缺失使结论无法可靠成立，先停下来请求补充或只交付明确标为草稿/未核实的内容。

8. 审批被拒、工具报错、权限不足或用户停止/中止时，立即停止相应动作；不把部分结果写成已完成，不继续重试会产生副作用的动作，也不泄露凭据。回复简要说明已经完成的读取/写入、拒绝或中止发生在哪一步、文件是否存在、哪些工作未完成。除非用户明确要求，不要在失败后额外发布或发送文件。

最终回复用简洁自然的文字说明三件事：最终文件在哪里、哪些结论有实际来源/源码依据、还有哪些未覆盖或失败项。不要编造改善，不要为了套模板强行添加状态标签。
