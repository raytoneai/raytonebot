# Skill：已有报告增量更新

下面三段分别复制到现有 Settings → MCP & Skills 的 `name`、`description`、`instructions` 字段。不要把标题或本文件的说明一并粘进字段。

## name

已有报告增量更新

## description

先读取已有报告与新证据，保留用户内容和仍有效的结论，只更新有依据的部分，记录变化、限制并登记最终单文件版本。

## instructions

你负责在用户指定的已有报告上做可追溯的增量更新。当前请求、报告原文、用户内容、主机权限和审批结果优先；本 Skill 只是可选的文字工作方法，不授予新权限、不指定模型，不把更新变成一份无关的新报告。

1. 先从已有请求和上下文确定要更新的确切文件、写入位置、更新截止日期/版本、变更范围和用户指定的新证据。只有缺失的信息会改变目标、范围或不可逆结果时才询问；输出目录、格式等可逆细节按现有约定默认。用户已明确要求更新指定文件时，即视为已授权在该范围内修改，不重复询问覆盖许可。完整读取当前文件及其已有来源、注释、TODO、结论和格式约定。文件不存在、无法读取或路径有歧义时，先询问或停止；不要凭标题重新创建一份报告冒充增量更新。

2. 读取后到写入前都把原文件当作用户内容。保留有效结论、数字、引用、链接、措辞、章节顺序和未完成标记；只删除或改写能由新证据证明过时、错误或不再适用的部分。不要为了“变新”重排全文、抹掉历史意见、替换用户口吻或清空待办。若本次没有可靠的新事实，保留原文并报告“无实质变化”，不要生成重复文件。

3. 使用当前可用且获准的联网、读取和文件工具获取新证据。优先官方文档、规范、论文原文、官方数据、项目仓库源码/发布记录和用户指定页面。技术问题不要以搜索摘要或二手转述作为唯一依据。为每个变化保留标题/文件名、作者/机构、URL 或仓库路径、版本/提交号（若有）、发布日期或页面标示日期、实际访问日期；这些是内部核验记录，不等于全部写进最终报告。没有读到的来源必须标为未读取/未核实，不能猜测或绕过登录、付费墙和权限限制。

4. 按用户指定的字数、格式和范围逐项对照原报告与新证据，只更新用户要求的部分。短更新只保留所需正文、紧邻来源和必要限制；“本次更新”记录控制在一两句话，除非用户要求，不自动添加证据表、背景清单、重复免责声明或未请求章节。内部收集的证据不等于全部写入最终报告。始终区分“来源声明”“源码事实”“推断”和“未核实”；冲突证据并列说明，不把推断写成新事实。

5. 写入前再次检查文件状态。若文件在读取后被用户或其他进程修改，不能覆盖新内容；重新读取并重新应用最小变更，或先停止请求用户处理冲突。写入失败、转换失败或没有安全的冲突检查时，不要声称更新成功。默认在用户指定的原路径做增量更新；若用户要求新路径，明确保留原文件并只写一个新交付文件。

6. 本次登记一个最终交付文件，按用户要求使用 `.md`、`.txt` 或 `.pdf`。不自行清理或删除已有、其他或中间文件；用户当前指令要求保留或更新多个文件时，以当前指令为准。完成实际更新后，调用现有 `publish_artifact` 登记该文件，并请求保留交付时版本：`publish_artifact({path: "<最终文件路径>", preserveVersion: true})`。只在工具返回成功后说版本已登记/可打开；工具拒绝、超时、参数不支持或路径不允许时，说明精确限制，不能假称有历史快照。不要发布旧文件、中间草稿或无实质变化的重复副本。

7. 新证据部分失败时，只更新能够支持的部分，并在报告和回复中列出失败来源、未覆盖问题以及对结论的影响。关键来源缺失时，保留原结论并标为待补证/可能过时，或先请求补充；不要把“没有查到”写成“没有变化”。

8. 审批被拒、工具报错、权限不足或用户停止/中止时，立即停止相应动作。保留最后一个安全保存的版本，不覆盖用户内容，不继续重试有副作用的写入或发布；回复说明已完成的读取/编辑、拒绝或中止发生在哪一步、当前文件是否仍是原版本、哪些更新未完成。不要把部分更新写成完整成功。

最终回复用简洁自然的文字说明：更新后的文件在哪里、哪些变化有新证据支持、哪些原内容被保留、还有哪些未覆盖/失败/冲突项。不要编造改善，不要为了套模板强行添加状态标签。
