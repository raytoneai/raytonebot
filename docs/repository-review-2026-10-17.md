## 2. 必须先修的问题

### 1. [P1] 另一会话能改变正在下载文件的保存归属

- **位置**：[browserService.ts:361](/Users/rickyhuo/RaytoneBot/src/pi/browser/browserService.ts:361)、[browserService.ts:214](/Users/rickyhuo/RaytoneBot/src/pi/browser/browserService.ts:214)。每次工具调用都改写共享 `currentSave`，下载完成时才读取它；只读的 `browser_accounts` 也会改写。
- **触发与实测**：会话 A 启动一个分两段返回的附件下载，在文件传完之前让会话 B 仅调用 `browser_accounts`，随后完成下载。真实 Chromium 结果是 A 的 `probe.txt` 调用了 B（builder）的保存回调，内容完整但归属错误。
- **影响**：下载会进入另一角色工作区，原任务找不到自己的文件，后续会话可能误用它。单用户的多会话场景即可触发，不需要多租户。动作串行队列和快照校验都没有保护异步下载归属。
- **最小修复方向**：在下载开始时按 download GUID 绑定发起动作/会话/保存回调，完成时按 GUID 回收；只读查询不能改写保存目标。无明确归属的手动下载要有固定规则。无需新增浏览器实例或面板。
- **验收**：A 慢下载、B 查账号/读快照/切页交错，A 文件仍落在 A；任务停止与手动接管后的下载不得被后来的任务接收。

### 2. [P1] 损坏的辅助配置被当作空数据，下一次保存会覆盖原文件

- **位置**：[memories.ts:69](/Users/rickyhuo/RaytoneBot/src/pi/memories.ts:69)、[routines.ts:102](/Users/rickyhuo/RaytoneBot/src/pi/routines.ts:102)、[mcpServers.ts:211](/Users/rickyhuo/RaytoneBot/src/pi/mcpServers.ts:211)；[channelStore.ts:35](/Users/rickyhuo/RaytoneBot/src/pi/imChannels/channelStore.ts:35) 也存在同类读取逻辑。
- **触发与实测**：给记忆、例行任务、MCP 各写入一份截断 JSON，然后重启对应服务。三者均正常返回空列表；再新增一条记录时，原文件直接被新列表替换，没有损坏提示或保留副本。MCP 使用关闭状态，未联网。IM 的同类逻辑仅静态核对，未额外触发连接器。
- **影响**：暂时的读取失败或文件损坏，会进一步变成不可恢复的覆盖。用户可能把“列表为空”理解为配置被删除，再添加记录，从而丢失旧任务、记忆或连接设置。
- **最小修复方向**：仅把 `ENOENT` 视为首次使用；其他读取/结构错误保持故障状态并禁止覆盖，界面报告原文件仍保留。复用 [conversationStore.ts:93](/Users/rickyhuo/RaytoneBot/src/pi/conversationStore.ts:93) 已采用的语义即可，不需要改数据库。
- **验收**：截断 JSON、错误结构、读权限失败都不能显示成正常空列表，也不能被普通保存覆盖；真正不存在的文件仍可首次创建。

## 3. 应当修的问题

### 3. [P2] 保存失败后仍保留新的内存状态，控制服务会卡在“准备中”

- **位置**：[control/store.ts:76](/Users/rickyhuo/RaytoneBot/control/store.ts:76)、[control/store.ts:97](/Users/rickyhuo/RaytoneBot/control/store.ts:97)、[control/server.ts:163](/Users/rickyhuo/RaytoneBot/control/server.ts:163)。`create/update` 先修改权威对象，再尝试落盘。
- **触发与实测**：把临时 `store.json` 的目标位置设成目录使 rename 失败，`claim` 报错；恢复可写后再次 `claim`，却返回 `created:false` 和 `provisioning`。冷启动 Store 列表为空。HTTP 路由仅在 `created:true` 时启动 provision，所以这次重试不会创建沙箱，且“失败重试”入口也不接受 `provisioning`。
- **影响**：一次存储故障后，页面可能一直等待一个从未开始的创建过程。相同提交顺序也出现在 [approvalMemory.ts:33](/Users/rickyhuo/RaytoneBot/src/pi/approvalMemory.ts:33)：实测清除授权写盘失败后，内存已无授权，重启后旧授权重新出现。清除接口会报错，本报告不把它描述成“成功撤权后被绕过”。
- **最小修复方向**：先构造下一份状态、保存成功后替换内存对象；写失败保持旧状态。审批授权存储也采用相同顺序。
- **验收**：真实 write/rename 失败后，内存与最后成功文件一致；恢复存储后重新 claim 能启动创建；授权添加/清除失败不能悄悄改变运行时状态。

### 4. [P2] 尚未送到引擎的长期记忆被提前记为“已展示”

- **位置**：[memories.ts:139](/Users/rickyhuo/RaytoneBot/src/pi/memories.ts:139)、[piHost.ts:861](/Users/rickyhuo/RaytoneBot/src/pi/piHost.ts:861)。`noteFor` 立即写 `shown` 版本，主机随后才校验附件并初始化引擎。
- **触发与实测**：保存一条“始终带计量单位”的记忆；首轮携带不存在的附件，主机返回错误且 bridge 收到 0 条 prompt；同一会话去掉附件重试，bridge 收到的有效 prompt 不再包含这条记忆。
- **影响**：用户修正一个附件或配置问题之后，助手会持续漏掉此前没收到的偏好，直到记忆版本变化或服务重启。现有 `unseenPrompts` 补发的是用户原文，不能补上被漏掉的记忆说明。
- **最小修复方向**：拆开“生成记忆说明”和“确认已交付版本”；只在引擎接受上下文后提交版本，接受前失败不消费。模型已接受后才失败的情况也要区分，避免每次无限重复注入。
- **验收**：附件校验失败、引擎配置失败后的有效重试带上记忆；正常续问不重复注入；记忆修改/关闭后仍发送正确更新。

## 4. 架构和质量判断

已有实现值得保留：

- **单一事件链路**：三引擎最终进入相同 AgentUX 事件与现有界面，工具、审批、产物不必再建平行 UI。`piAdapter`、回放身份与终态测试使这一选择有实际支撑。
- **主会话持久化较扎实**：关键回执先落盘，保存失败有显式反馈；原生上下文缺失时拒绝假装续接；重启标记中断而不盲目重放。辅助配置存储应补齐到同一标准。
- **浏览器控制边界已成形**：真实 Chromium、独立 worker、出站代理、快照归属、动作前事实复核、人工接管、popup/标签页、持久 profile 都有实现及部分实机证据。下载归属是这条链上的具体遗漏。
- **文件与 HTML 预览有实际内容和隔离**：工作区下载做路径/链接校验；HTML 用 opaque-origin iframe 和 CSP，审批前预览另外限制脚本。它们超出了纯界面原型的程度。
- **没有必要整体换后端**：当前主要问题在状态边界和交付验证，换成完整 OpenXX 栈不会直接消除它们。

需要关注的工程边界：

- `piHost.ts` 约 1,857 行、`agent-shell.tsx` 约 1,665 行；文件长度本身不算缺陷。真实风险在新增模块重复发明了不同的保存失败语义。先修上述具体问题，再随功能修改抽离明确责任，不做大规模拆文件。
- 未发现已提交的 `.github/` CI 配置，`npm test` 也不包含 Python 运维测试。当前本机测试齐全，但新改动是否必经 Node、Python 与 Linux 隔离检查，没有仓库内自动门禁证据。
- 构建的大 chunk 提示需要和首屏加载数据一起评估。three 等部分库按需加载，不能仅凭最大 chunk 推断首页慢；本轮未测首屏耗时和慢网表现。
- `docs/product/README.md`、`01-product-brief.md` 与 `11-parity.md` 的摘要明显落后于后面的日志。例如 MCP/记忆已有 10 月 13 日 BU 组云端三引擎实测，旧对齐表仍写“工作树、云端未验”；README 仍称例行任务没有按时运行。应让摘要链接到最新验收，而不是再沿用旧百分比。

本轮没有发现必须为了单用户负载新增数据库、消息服务或第二套 Agent 后端的依据；也没有给出无依据的“可删多少行/依赖”估计。

## 10. 推进建议

1. **先收紧可靠性边界**：修问题 1–4，新增对应失败场景回归；重点复用主会话已建立的“保存成功才更新内存”和“不可读不等于不存在”。
2. **把同一版本交付闭环做实**：明确目标提交；三引擎执行相同任务，覆盖审批、停止、刷新恢复、文件产物、MCP、记忆与浏览器慢下载；分别记录本机/测试实例/生产，不混用历史证据。
3. **完成已选择的常驻管理路线**：接通正式登录/现有 console 工作、常驻 keeper、可监测备份、暂停唤醒和目标环境恢复演练。先整合现有 control，不另建平行管理服务。
4. **若主打协作，补持久任务对象**：最小范围是 task/assignment 的负责人、父子关系、结果身份、停止传播和重启后的待核对状态；随后才考虑依赖和共享浏览器/工作区资源调度。入口继续扩展现有 owner。
5. **若主打知识工作，先写 Spaces 一页规格**：文档如何从对话产生、在哪里继续编辑、怎样检索；不能仅把产物列表重命名成知识空间。此项与协作路线可按实际使用选择先后。

总体判断：现有架构可以继续推进；应先修已经复现的数据/归属错误并完成交付验证。完成度的主要增长空间在长期任务与文档知识工作，继续堆展示功能很难补齐这两块差距。
