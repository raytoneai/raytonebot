# Jev 类判断模型与 Agent harness：近期用法调研

调研日期：2026-10-04。只查官方文档、项目作者仓库和原始研究；未安装集成、调用收费模型或修改运行代码。本文的推荐是针对 RaytoneBot 的设计判断，不是已验证的产品收益。

## 结论

值得继续研究。上一轮 Laya 试验衡量的是单次判断；harness 的价值还取决于如何提供状态、限制问题、复用结果、处理不确定和验证执行。**优先试验工具/技能推荐、子任务边界的模型分流，以及固定工作流中的语义分支。** 暂不让 Laya 单独判定任务完成或解除执行约束。

不同模型的效果不能互相代替：Jev 的集成案例不证明 Laya 有相同能力。我们实测的 Laya 多语版在中文主测试为 31/44，高置信度错误也存在。详见 [本机实验报告](/tmp/raytone-laya.vbSfFo/REPORT.md)；该目录是临时文件，不保证长期保留。

## 最近的关注点与成熟度

## 三个最适合我们的试点

以下数字和流程是建议，未实现、未测量。

### 1. 从工具清单中推荐几张用法卡片

已有方向是“sandbox 预装 CLI，harness 给 Agent 本地工具清单”。可以先保留完整的短索引，再按当前任务附加少量最相关的用法：

`请求 + 当前文件类型 → 候选工具/技能 → 窄判断 → 推荐用法卡片 → 主 Agent 选命令 → 现有 shell 执行`

例如“分析 Excel，制作 PDF 报告”：推荐数据读取/统计、报告生成和 PDF 检查用法。文件扩展名、工具是否存在、版本兼容由代码处理；模型只判断用户要分析数据、保留排版还是提取内容。

初期推荐 3–5 个条目即可，不删除完整索引，不隐藏主 Agent 可搜索的其他工具。推荐错了可以继续查目录，降低错误代价。工具很少时，直接给短清单可能更好；需要与静态清单和关键词方案比较，不能预设加入判断模型一定有收益。

[pi-jev 的技能错选复盘](https://github.com/TheoOliveira/pi-jev/blob/main/docs/skill-routing-investigation.md)值得直接参考：主题相关不等于技能适用，选择条件要写清具体操作、产品和工作流；候选召回漏掉正确技能时，后面的判断无法补救。其修正后的成绩来自开发样例，仍需要独立测试。

### 2. 主 Agent 保持稳定，在子任务开始时分流

由主 Agent 给出明确任务、输入和验收条件，判断模型只回答少量条件，例如“是否为按既定步骤做机械处理”“是否需要新方案”“是否依赖前文推理”。由 harness 将这些结果与客观条件合并，选择 worker 能力档位。

例子：检索函数位置或整理材料可候选较便宜 worker；跨模块故障诊断继续交给较强 worker。生成自由文字、分解开放任务仍由生成模型完成；不要让判断模型仅凭模型名字猜谁更擅长。

优先在新任务、子 Agent 启动或独立旁路任务做选择，同一工具循环保持模型稳定。近期 [Harness Tokenomics 研究](https://arxiv.org/abs/2609.28919)专门分析了缓存重建成本，报告的 13–21% 节省来自企业工作负载模拟和指定价格假设，并非线上对照实验。其可借鉴点是把缓存、重试和错误分流一起计费。

用户明确选定的模型保持优先。不确定、路由失败或目录不匹配时沿用既有路径。不能将“模型回答很自信”当作无需验证的降档依据。

### 3. 把重复操作整理成固定流程，模型仅选择语义分支

例如批量处理文档：

`代码检查文件/提取文本 → 判断文档用途 → 选择已验证模板 → CLI 转换/填充 → 代码检查页数、字段和产物 → 复杂例外交给主 Agent`

大模型先设计流程和异常分支，后续批量运行复用；小模型处理合同/会议记录/账单等边界明确但难写规则的语义分类。我们刚才的 Laya 错例意味着这些类别仍需用业务样例验证，尤其应包含“会议纪要里讨论发票”之类的干扰。

需要跨步骤依赖的判断分阶段执行；同一状态上相互独立的问题可合并为一批。例如文档类型与语言可以并行，依赖“文档类型”结果的下一轮专用问题则后置。官方明确说明同一调用的问题独立读取共享状态，不会相互读取答案。[TypeSafe 接口原理](https://docs.typesafe.ai/introduction)。

## 实现形态的建议

不需要引入 MCP 或新的编排服务。先把判断能力作为现有 harness 的可选本地步骤：批处理可一次进程处理多项；高频调用可复用一个 stdio 子进程，避免每次 shell 调用重新加载权重。[subagent-dispatcher 的本地适配](https://github.com/togishima/subagent-dispatcher#why-a-local-semantic-evaluator)已有类似做法，但它使用的模型/硬件数据不能当作我们的数据。

代码负责事实和动作边界：已安装工具、可用文件、数值、退出码、权限、预算。模型负责很窄的语义问题。实际执行保留现有三引擎和工具生命周期，不增加平行 UI 或把任务选择变成权限授予。

官方 Jev 1.13 也记录了数字/日期比较、复杂间接关系、冗余状态、选项顺序和对抗性输入等局限。状态构造与问题描述是实质工作；输出形状固定并不保证答案正确。[官方局限，2026-10-02 更新](https://docs.typesafe.ai/model-jaggedness/jev-1.13)。

## 下一轮该如何证明有用

先收集一批具有实际任务结果的中文样例，分开开发集和未用于调提示词/阈值的测试集。比较：当前 harness、简单规则、Laya 辅助；有 Jev 访问条件时再作为单独对照，不能用社区成绩代替。

先旁路记录建议，不改变执行结果。随后只在可恢复的用法推荐或独立子任务上试点。共同统计：

- 最终任务成功率及遗漏的必要工具，而非只看分类命中。
- 首次分流成功率、升级和重做次数。
- 每个成功任务的总成本与耗时，包含判断、加载、缓存失效和重试。
- 不确定时的覆盖率，以及被错误自动处理的比例。

对 Laya 最先值得测的是“工具用法推荐”，再是“固定文档流程分支”。模型降档需要真实完成结果作为标签；泛化的自动验收和审批判断继续后置。
