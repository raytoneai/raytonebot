# RaytoneBot 优化优先级与最小改造方案

日期：2026-11-01。方案依据：`c0b1f352fcc7ea4e1b3c3db6d4431da24783f3e0` 的相关实现；上游沿用 [OpenDuet `677e0fc`](openduet-source-research-2026-11-01.md) 与 [OpenMausBot `8c663d2`](openmausbot-source-research-2026-11-01.md) 的固定源码研究。下文保留方案阶段的排序、候选契约和验收要求。

**后续实施状态**：用户随后授权首批优化，已在本机实现两条文本 Skills 和显式交付版本，并将 Skills 分配给现有 Raer。版本支持 Markdown、文本和 PDF，复用原 Output；其余候选未实施。真实模型完成正常研究/已有报告更新对照，但字数要求未完全达标、样本不足以证明 Skills 改善质量。已通过的工程检查、尚未验证的四类模型异常场景见[首批验收记录](../output/first-batch-optimizations-2026-11-01/README.md)，实施决策见 [ADR-057](product/07-decisions.md#adr-057任务-skills-复用现有配置显式交付可保留文件版本2026-11-01)。

## 建议先做什么

**首批只做两项：两条可验收的任务 Skills，以及明确交付文件的版本保留。** 第一项验证已有能力能否稳定完成真实工作；第二项修复“过去交付的文件重新打开却变成新内容”的明确产品缺口。第一项通过后再做第二项，避免同时扩大范围。

排序以当前单用户、本机/云主机共用、研究与文档工作为假设。依据是本次实际使用和源码缺口，没有用户频次统计或同模型对测，不给虚构收益分数或精确工期。S/M/L 是相对改动规模，不是排期承诺。

| 顺序 | 优化 | 收益与排序原因 | 最小范围 / 改动规模 |
| --- | --- | --- | --- |
| **1 · 首批** | 两条任务 Skills + 清楚的交付要求 | 本次对话已反复使用“研究→报告→更新”；现有工具和入口已齐，可直接验证收益。 | 仅 Skill 文本与配置，不新增 schema、插件或界面；S。 |
| **2 · 首批** | 明确交付文件保留当时版本 | 当前历史产物引用实时路径，内容会随覆盖变化；影响研究结果可追溯性，收益确定。 | 只处理显式登记的单文件交付；主机文件存储 + 既有 Output；M。 |
| **3 · 第二批** | 一条例行检查的覆盖范围与重复结果控制 | 借鉴 OpenDuet 的已检查/未检查区别；先有可信变化依据，才能减少重复报告。 | 一种确定的数据输入与结果规则，复用 routines；M，泛化后会明显变大。 |
| **4 · 按实际阻碍补** | 任务需要的能力检查 | 已有 MCP 测试、模型检查与配置续接；新增全局 Setup 会重复已有能力。 | 先写入第 1 项的任务要求；只有反复遇到的缺工具/账号问题再补结构化检查；S–M。 |
| **5 · 有复用需求再做** | 团队配置包 | 借鉴 OpenMausBot，但单用户当前尚无频繁安装/分享整组 Bot 的证据。 | 首版最多角色、文本 Skills 与成员关系；多存储导入、预览与失败回收，至少 M。 |
| **6 · 有调用方再做** | 对外 CLI/MCP + 协作等待 | 便于 Codex/脚本调度，但当前没有确定调用方；鉴权、取消与完成语义都需完整定义。 | 复用同一主机的有限接口，不再建执行引擎；M–L。 |

交付版本的优先级来自本项目缺口和既有产物研究，**不是因为两个新项目已经提供同等能力**：OpenDuet Make 是原地保存与冲突检测，OpenMausBot 团队包是配置复用。

## 第 1 项：先用两条 Skills 验证完整任务

### 用户能得到什么

1. **带来源的研究报告**：读取用户指定的一手资料，区分来源声明、源码事实和推断，生成可打开的 Markdown 文件，并登记为产物。
2. **已有报告的增量更新**：先读现有文档和新证据，保留用户内容与仍有效的结论，修改过时正文，说明本次变化及未覆盖部分。

交付只要求说清三个事实：成果在哪里、哪些结论有证据、还有什么未完成。仅在有关时说明部分失败，不给普通回复强加模板标题或状态标签。审批拒绝、缺能力、来源读取失败和用户停止，都不能写成任务已完整完成。

### 最小落点

- 先将两份可审阅的 Skill 文本作为内容文件维护；通过现有 Settings → MCP 中的 Skills 编辑器保存，再由原 Bot 编辑器分配。现有 `name / description / instructions / enabled` 足够，不添加 `requiredTools`、自动导入器或内置模板注册中心。
- 所需能力以普通文字写在步骤内：研究使用现有联网工具；文档读取/修改沿已有文件工具和审批；完成后调用现有 `publish_artifact`。无能力或授权失败时走既有配置续接；访问过设置不等于连接已验证。
- 不把 Skill 文本当权限、不指定新模型。先选当前实际使用的一个 Bot/引擎做真实验证；其他引擎未验就不声称通用通过。
- 尚不增加欢迎页卡片或 `/` 命令。验证确有收益、且使用入口成为实际阻碍后，再决定是否在原 Composer/欢迎区增加便捷入口。

涉及现有 owner：[SkillsSection](../src/components/settings/SkillsSection.tsx)、[Bot Skills 主机](../src/pi/botSkills.ts)、[产物登记](../src/pi/artifactTool.ts)。第一阶段预期无需改这些文件，只使用已有能力。

### 如何验收

用相同模型和权限，对照普通请求与使用 Skill 的请求，记录来源正确性、人工纠正次数、文件能否打开、失败是否如实表达。固定六种输入：正常研究、部分来源失败、更新已有报告、更新时发现文件已变化、审批拒绝、用户中止。正常任务重复执行应保留用户内容；失败场景不得产生假成功或重复对外动作。

不因“加载了 Skill”就认定有效，也不为两份文本新建评测平台。使用现有测试资料与人工核对记录；若未见改善，调整/停用文本即可，暂不继续建设模板体系。

## 第 2 项：只给明确交付的文件保存版本

### 当前缺口与最小契约

`artifactTools` 现在校验文件后关闭句柄，登记真实文件 URI；历史没有文件字节。`artifactCatalog` 在同一会话内按路径保留最新项，预览读取当前工作文件。因此只多加版本号或时间戳不能解决问题。[登记实现](../src/pi/artifactTool.ts)、[查询实现](../src/pi/artifactCatalog.ts)、[ADR-043/044](product/07-decisions.md)

建议扩展现有 `publish_artifact` 的一个可选参数 **`preserveVersion: true`**；默认省略仍按原行为登记。上述两条 Skills 在最终交付时才请求保留。先支持 `.md`、`.txt`、`.pdf` 等明确列出的单文件格式；先不处理 HTML 关联资源、目录、压缩包、音视频或每次临时写入。

### 一条完整的数据流

1. **登记时捕获**：复用 `openWorkspaceFile` 的路径、私有目录、链接及文件类型检查，从已经校验的句柄读取有界内容；读取前后核对文件状态，检测到变化就拒绝保存该版本并要求重新读取。先持久保存字节与索引，再发原有 artifact 事件。失败不回报“版本已保存”。
2. **存储归主机**：在数据目录旁新增仅供主机管理的文件区，例如 `<dataDir>.artifact-versions/`，不增加数据库，并纳入现有私有路径/子进程隔离与备份范围检查。每项记录主机生成的版本 ID、原会话/轮次/产物身份、原路径、类型、时间、大小与内容 hash；保存后的字节不通过产品编辑接口覆盖。内容不写进聊天日志，也不由 Agent 提供存储路径。
3. **读取沿原接口**：扩展现有鉴权下载路径，允许按交付身份读取版本；主机验证会话归属并查内部索引，不能信任客户端提交的任意磁盘路径。版本读取不依赖原工作文件仍存在。无版本的旧记录继续表示当前工作文件，不伪装补出了历史内容。
4. **选择沿原 Output**：查询结果可关联版本记录；原产物详情内显示“交付时版本 / 当前工作文件”与时间，版本有多项时原位选择。必须解除版本记录被路径去重吞掉的问题，群产物按持久身份匹配，不能靠文件名。打开旧版只读，不自动覆盖工作文件。

实现集中在一个主机版本存储模块，登记和读取是其小接口；复用原事件类型，保持 vendor 不动。主要接入位置为 `artifactTool.ts`、`piRuntimeController.ts`、`piHttpHost.ts`、`artifactCatalog.ts`、原文件预览/下载客户端及 Output 所属 helper。需一并核对 `workArtifacts` 的路径去重、`artifactContent` 的已打开标签刷新和 PDF 下载地址校验，不能只改后端存储。[控制器](../src/pi/piRuntimeController.ts)、[文件入口](../src/pi/piHttpHost.ts)、[列表投影](../src/runtime/workArtifacts.ts)、[标签刷新](../src/runtime/artifactContent.ts)、[预览](../src/components/agent-preview/outputframe/useFilePreview.ts)

### 有意限制首版范围

- 建议单文件上限沿用当前预览的 **20 MiB**，主机总量初值 **500 MiB**；这两个值是方案默认值，后者没有用量测量依据，可在实施前调整。达到上限拒绝新保存并说明原因，不静默删除旧版。
- 显式再次登记可生成新版本，不覆盖旧版；读取/下载重试没有写入副作用。首先不做跨文件全局去重、全文搜索、可视 diff、回滚覆盖或自动保存每次编辑。
- 版本与来源会话同生命周期，现有删除路径需清理所属索引/字节；临时文件和崩溃孤立文件不得进入查询结果。跨文件写入不宣称数据库式事务，正常失败需清理，重启读取要识别未完成写入。
- Markdown 只保存文件字节，不冻结其外链资源；云实例销毁后的恢复仍取决于备份与磁盘保留。该能力不是跨实例备份。
- 这是对 ADR-044“只登记、不保存字节”范围的显式扩展。实施时补决策记录；本轮不把候选写成已采纳决策。

### 如何验收

同名文件先交付 A、改为 B 再交付，两个版本分别返回 A/B；覆盖或删除当前文件后旧版仍可打开，重启后身份和字节一致。补充磁盘失败/配额、捕获期间文件变化、私有路径/链接拒绝、重复登记、会话删除与群产物归属验证。没有快照的旧会话保持原行为。

改动后跑定向测试、构建和跨模块回归，HTTP 接口检查及全部事件 fixture；实际浏览器走查 Markdown/PDF、当前文件切换、历史版本和窄屏。再用实际使用的引擎完成一次两次交付任务，不把测试文件生成当真实模型验收。

## 第 3–6 项的进入条件

**例行任务**：先选一条来源固定、能取得稳定 ID/内容摘要的检查任务。保持执行状态与业务结果分开；未来只增加可选结果信息，例如变化、无变化、部分检查、未知。缺来源、截断、读取失败或有效基线缺失时，不能判为无变化，也不能更新“上次完整检查”基线；运行错误仍用既有 error。不要解析助手的一句“没变化”决定静默。

首个增量只考虑避免重复生成同一交付文件，保留任务执行记录、失败、审批及真实消息；不事后删除已经流出的回复。完全不产生回复会涉及运行和展示路径，另定范围。仍沿 `routines.json`、原 Settings 任务记录和来源会话，不加 worker、通知系统或新结果标签。

**能力检查**：第 1 项先验证任务说明和现有入口是否足够。只有重复遇到某个具体工具/账号缺口，再为该路径组合“配置存在、工具可用、授权有效、业务读取成功”的检查；已有 MCP `tools/list` 不能证明 Gmail 等业务读取一定成功。检查失败不自动重新执行结果不明的原动作。

**团队包**：进入条件是实际需要反复部署/分享同一组配置。最小包只含角色文本、文本 Skills、群成员关系；首版排除 routine、MCP、记忆、模型、权限、凭据和历史，避免一开始承担全部存储的回滚与授权语义。复用原 Bot/群入口做审阅和创建，新身份不覆盖旧配置，Skills 默认关闭。不能拿现有旧浏览器迁移接口直接收外部包；新入口先按 AGENTS 规则补一页 owner 与验收规格。

**外部 CLI/MCP**：进入条件是明确有一个真实调用方。先约定发送、查询/等待、读取有界结果、停止的最小集合，保留请求身份和取消，审批仍由用户在现有入口完成；不暴露配置写入、删除或凭据。沿已有 `group.tasks` 汇总必须等待的委派，区分停止/失败/待核对，不能仅凭父轮结束判成功。只实现调用方需要的一种包装，不同时造 CLI 和 MCP 两套入口。

## 本轮产出与后续顺序

方案阶段交付为优先级和候选契约，当时未安装 Skills、创建例行任务、改运行参数或写产品代码。后续首批实施及实际验收以本文开头链接的记录为准；下列建议顺序不代表其余候选已经启动。

建议执行顺序：**两条 Skill 文本与真实任务对照 → 明确交付文件快照 → 按实际失败/噪音选择一条例行检查或能力检查**。团队包、外部控制、桌面分发、语音、更多连接器和完整任务看板不进入首批。
