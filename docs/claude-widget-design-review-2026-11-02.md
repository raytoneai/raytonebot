# Claude 微件规范对照评审（2026-11-02）

结论：RaytoneBot 主界面已经有克制的视觉方向、语义 token 和浅深主题。优先补齐 HTML 产物的 SVG 可读性与流式生成约定，其次改善触屏消息操作和手机设置导航。没有重做主界面、替换图标库或引入新组件体系的必要。

后续分批实施与验证见[优化记录](../output/design-optimizations-2026-11-02/README.md)；下文保留实施前的测量和评审结论。

本文是评审与建议，不是已采纳的开发规范；未修改产品代码。用户提供的转载未附可核验来源，本次不确认其“内部提示词泄露”的说法。根据其中宿主界面、iframe、预加载库和流式输出等约束判断，它主要描述内嵌微件，不能推广为整个 Web 应用的通用规则。

## 当前已具备的基础

- [.impeccable.md](../.impeccable.md) 已明确单用户、克制、清晰、有亲和力，以及现有头像、消息行宽和组件职责。
- [themeTokens.ts](../src/theme/themeTokens.ts) 已用 Radix 色阶组织表面、文字、边框、状态和浅深主题；[app.css](../src/styles/app.css) 已定义间距、字号、控件高度和动效 token。
- [artifactTheme.ts](../src/components/agent-preview/outputframe/artifactTheme.ts) 已向 HTML 产物注入主题变量、基础控件样式和 SVG 色类。
- [rolePrompt.ts](../src/pi/rolePrompt.ts) 已说明离线沙盒、内置图表库、键盘与标签、360px 换行、减少动画、数值校验和 `raytone.sendPrompt()`。
- 主应用实际界面使用中性色面、少量状态色与独特的 Bot 头像；聊天、审批、输入和输出沿既有 owner 展开，没有明显的通用 AI 落地页式装饰。

## 优先问题

### P1：SVG 节点文字与背景需要分别配色

位置：[artifactTheme.ts](../src/components/agent-preview/outputframe/artifactTheme.ts) 第 9–11、31–32、45 行。

当前 `.c-*` 的颜色不随主题变化；节点淡色背景、边框、文字使用同一个基础色。普通 SVG `<text>` 也没有默认的语义文字填色，`body { color: ... }` 不会自动替代 SVG 的默认 `fill`。

用实际主题生成 CSS，在 Chromium 中渲染 14px 标签和 16% 节点底色，再根据计算样式计算对比度：

| 样本 | 浅色节点文字对比度 | 深色节点文字对比度 |
| --- | ---: | ---: |
| blue | 2.99:1 | 3.93:1 |
| teal | 2.10:1 | 5.46:1 |
| amber | 1.86:1 | 6.12:1 |
| purple | 3.39:1 | 3.50:1 |

全部八种浅色节点样本为 1.86–3.39:1；未设 `fill` 的普通 SVG 文字在深色页面上为黑色，对比度约 1.19:1。这是基础样式的受控复现，不代表所有已有产物均使用该组合。[WCAG 普通文字对比度基准为 4.5:1](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum/)。

建议：在现有 `artifactThemeCss()` 内分离节点背景、描边与标签色，使用已有 Radix 浅深色阶；补充普通/次要/标题文字的显式语义类，并同步生成指引。不要仅提示模型“使用色类就会兼容深色”。数据图仍需保留颜色以外的标签或图例。

验证：浅深主题下分别检查普通 SVG 文字、八种节点色、标签对比度及状态区分；保留图形自身的显式样式能力，不全局覆盖任意插画的填色。可从 `/audit` 开始。

### P2：把流式首屏约定写进产物提示词

位置：[rolePrompt.ts](../src/pi/rolePrompt.ts) 第 41–49 行；[htmlPreview.ts](../src/components/agent-preview/outputframe/htmlPreview.ts)；[liveHtmlWrite.ts](../src/runtime/liveHtmlWrite.ts)。

流式预览会清除脚本并禁止事件处理代码执行，这是保存/审批之前的既有边界。提示词却未说明先输出可见 HTML。Chromium 通过真实 `htmlStreamDocument()` 和消息更新通道验证：

| 写法 | 流式阶段 |
| --- | --- |
| 空容器，靠脚本生成内容 | 无可见文字 |
| 内容 `display:none`，靠脚本显示 | 无可见文字 |
| 静态内容先出现，脚本随后增强 | 内容可见 |

建议：在原 `INTERACTIVE_ARTIFACTS` 中补充“短 style → 有用的静态 HTML/SVG → script”；主要内容在脚本未执行时可读；图表可先给数据摘要或静态示意，保存成功后增强；流式阶段不把全部内容藏进待脚本切换的容器。保留脚本禁用边界。

验证：分段输入 HTML，检查首段可见内容、完整内容和保存后的交互。不同引擎的工具参数到达顺序决定实际流式程度，不能据此承诺所有引擎逐字预览。可用 `/clarify` 精简指引。

### P2：触屏消息操作扩大点击区

位置：[app.css](../src/styles/app.css) 第 1991 行 `.message-action-icon`、第 9220 行触屏规则。

390×844、`hasTouch: true` 的浅深色群聊中，复制、重发、重新生成按钮实际均为 28×28px。现有触屏规则已扩大输入区和侧栏按钮，未覆盖消息操作。

建议：在既有 `MessageActions` 样式中将触屏点击区扩大到约 44×44px，图标仍保持当前尺寸；这是项目触屏一致性建议，不将 28px 直接判为 WCAG 最低标准违规。

验证：触屏媒体条件、相邻按钮间距、长消息、左右消息与窄屏换行；保留现有可访问名称。可用 `/adapt`。

### P2：手机设置改用可发现的分类入口

位置：[SettingsDialog.tsx](../src/components/settings/SettingsDialog.tsx) 第 148 行；[settings.css](../src/components/settings/settings.css) 第 575 行。

普通模式的设置有 11 项导航，390px 下横向总长度约 1068px。首次仅显示模型服务、权限、IM 频道及部分例行任务；记忆、登录凭据、外观位于屏外。已有导航逻辑能把选中项滚入视野，问题是初次发现后半部分功能的成本。

建议：沿原 `SettingsDialog`，在窄屏用现有选择控件显示当前分类并展开全部入口；桌面保留现有侧栏。不要再增加设置面板。

验证：中文/英文/日文、390px、键盘操作、初始分类与切换后的内容定位。可用 `/adapt`。

### P3：收敛字重与设计约定入口

位置：[app.css](../src/styles/app.css) 第 34、52、3239 行；[settings.css](../src/components/settings/settings.css) 第 188 行。

已存在语义字重 token，但实际抽查出现 `400/500/560/600/620/650/700/760`。审批按钮仍直接使用 760，设置标题直接使用 650。`app.css` 的结构 token 注释还指向不存在的 `docs/COMPONENT_SYSTEM.md`。

建议：按正文、标签、标题、关键动作归回现有 token；是否减轻审批按钮字重需保留动作区分，不强制全站只能用 400/500。把可执行的设计原则补入现有 `.impeccable.md`，修正失效引用，无需新建第二套设计系统。

长回复正文当前实测 14px/22.12px。独立阅读字号 token 可作为后续对照试验，但短消息截图不足以证明必须改成 16px。可用 `/typeset`，实施最后用 `/polish` 收尾。

## 对转载规则的取舍

| 规则 | 本项目处理建议 |
| --- | --- |
| 语义 token、浅深主题、无障碍名称、紧凑布局 | 采纳原则，补齐现有实现缺口 |
| style → 可见内容 → script | 适用于本项目流式 HTML 产物 |
| 解释文字放聊天，微件聚焦视觉和交互 | 适用于辅助解释微件；独立报告/可下载页面仍需标题、单位、来源和必要说明 |
| 固定 Anthropic 字体、Tabler 图标 | 不迁移；主 UI 已有字体与 Lucide，Phosphor 用于少量品牌标识，产物未预载 Tabler |
| 禁止所有手写 SVG | 不迁移；现有品牌头像与图解需要 SVG，通用 UI 图标优先复用已有库 |
| 全局禁止 tabs / display:none / fixed | 不迁移；只限制流式阶段对隐藏内容和脚本的依赖。Output iframe 高度由面板分配，不是转载中的自动撑高容器 |
| 禁止任何阴影、模糊、渐变 | 采用“装饰要有用途”的原则；弹层层级、焦点、滚动提示等需按具体用途判断 |
| 全局禁注释、Emoji、句中加粗 | 不迁移；与代码可维护性、用户内容及独立文档目标无直接关系 |
| 固定 680px、同排最多四框、最多两组颜色 | 改为按实际面板宽度折行、控制信息密度、颜色有明确语义；不硬删数据图的必要类别 |
| 需要模型响应的交互调用 sendPrompt | 与现有能力一致；交回对话时调用 `raytone.sendPrompt()`，本地计算继续本地完成，保留点击与队列约束 |

建议给产物生成指引增加的内容可控制在六条：静态首屏优先；复用主题/基础控件；普通文字与 SVG 文字分别使用语义色；颜色承担含义并提供标签；辅助微件减少重复说明；布局适应实际面板宽度且触屏可操作。不要把整篇转载塞进每轮系统提示。

## 评审交叉验证

独立主 UI 评审暂评 28/40，仅描述本次抽查场景，不是完整可用性认证；不包含产物 SVG 与流式实验的单独评分。

| Nielsen 项目 | 0–4 分 | 观察 |
| --- | ---: | --- |
| 系统状态可见 | 3 | 审批与运行状态已有呈现 |
| 贴合用户语言 | 3 | 主路径清晰，设置仍有专业术语 |
| 用户控制与退出 | 3 | 保留停止、取消与关闭入口 |
| 一致性 | 3 | 主题和 owner 稳定，细节字重可收敛 |
| 错误预防 | 3 | 现有审批与输入约束 |
| 识别胜于记忆 | 2 | 手机设置后半导航难发现 |
| 效率与灵活性 | 3 | 主聊天路径紧凑，触屏操作可改善 |
| 简洁与美感 | 3 | 中性色与 Bot 身份有一致方向 |
| 错误恢复 | 3 | 有恢复呈现，未复验所有故障链路 |
| 帮助与说明 | 2 | 部分设置概念仍需用户理解 |

认知负担八项检查中，聊天未发现显著失败；手机设置的分块与选择呈现有两项改进空间（2/8，中等）。单手手机用户最受按钮尺寸和横向导航影响；熟练用户应保留现有紧凑主路径；低视力/键盘用户需要后续长文缩放和屏幕阅读器验证。

确定性扫描 `npx --yes impeccable --json --fast src/components` 返回 exit 2，仅有两条侧边线提示：Markdown 引用的 3px 线和任务恢复提示的 2px 中性线。前者有明确语义，后者至多为低优先级视觉取舍，不作为本轮重点。CLI 已废弃并忽略 `--fast`。live overlay 因检测器要求其自身的 PRODUCT.md/DESIGN.md 返回 `context_missing`，未启用，也未因此改造仓库。

浏览器计算样式扫描覆盖 26 个视图组合：1280/390px、浅深色、欢迎页、普通文本、审批、错误、demo、终态事件，另含桌面设置。可见元素中未发现低于 11px 的文字、未命名图标按钮、页面横向溢出或元素渐变背景。此扫描不涵盖伪元素、iframe、全部设置分区及所有交互；SVG 与流式内容由独立实验验证。

代码 grep 中的旧 `am-*` 小字号、被后续规则覆盖的 `.step-kind`、图标化发送按钮的 `font-size:0`、品牌颜色均已从问题清单中过滤。没有把“扫描命中数量”当成产品缺陷数量。
